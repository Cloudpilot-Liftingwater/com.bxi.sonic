# ELF3 VLA 数采积压与时间错位

日期：2026-10-21。以下保留修复时的离线记录。后续v15已现场复测：保存/弃用和暂停续采通过，未再观察到此前秒级混配；状态和相机仍有毫秒级时间差。当前发布见../../docs/RELEASE_20261026.md。

## 现象与影响

v14现场能保存、弃用和暂停恢复，三路视频及数值也能读回，但写入速度约35行/秒，低于实际推理目标50Hz。107条录制/暂停状态中86条接收队列到达32条上限。第一条保存的1626行中，关节状态比对应token晚：中位5.101秒、最大5.801秒；头部画面晚约5.022秒（中位数）。文件没损坏，时间语义已经损坏。

同段SONIC日志仍约60秒3000个控制周期，不能把数采35行/秒描述为模型持续只有35Hz。录制期间有周期抖动，但机器人动作延迟究竟有多少来自输入/网络/CPU竞争，现有证据不足以分摊。

## 根因链条

```text
真实推理约50Hz → official_node.inference
                 ↓ 接收时取最新状态、IMU、图像快照
                 ↓ queue.put：32条满后等待
官方writer / 1080p编码跟不上 → 接收回调阻塞
                 ↓
新token在DDS可靠队列（深度256）继续积压
状态/图像回调仍在更新最新缓存
                 ↓
恢复接收时处理几秒前的token，却取此刻最新状态/图像
```

**只把writer放到另一个线程并不足以隔离背压。**生产者如果在满队列里等待，负载仍会反传到接收层。已有“快照不变”单元测试只证明入队之后不变，漏测了token尚在DDS等待时缓存已变的情况。

## 为什么处理慢：已测与未测分别说清

本地使用现场真实RGB纹理（头1920×1080，两腕640×480）对旧writer逐阶段测量：

- 600行总计9.914秒，纯writer约60.52行/秒。这是更强工作站上的上限，不是机器人35Hz的重现。
- 主线程9.136秒中，约5.93秒在视频队列等待；约2.99秒在官方exporter的deepcopy。头部队列49/50，腕部队列很低。
- 旧版将所有视频编码限制为1线程。头部RGB转VideoFrame约4.39ms/帧，encode+mux约12.06ms/帧；头部是本机实测瓶颈。
- 实际ROS适配还使用8线程executor，在每个约1kHz状态/IMU回调中进行关节排序、数组和四元数计算。v15将这些计算降到每个实际50Hz推理行。它是确定存在的多余工作，但没有现场CPU剖析来宣称它贡献了全部35Hz问题。

所以：**视频背压加接收阻塞导致错位已证实；单线程1080p编码是本机复现出的主要吞吐瓶颈。现场35Hz中编码、调度、内存搬运、磁盘各自占比仍待新版计时。**不能把“相机30Hz”解释成“数采必然35Hz”，也不能直接说无线网络是根因。

## v15最小修复

1. **仍用官方写入。**RecordingCommands、EpisodeState、Gr00tDataExporter、官方清理/合并和GR00T统计算法不重写。Exporter只保留原有import适配；VideoWriter本地生命周期补丁及新增计时均有可审计diff。
2. **接收不等写盘。**保留32条有界队列，改为立即入队；满载明确停止本记录器接收，已接收快照排空后以interrupted保留。不会继续积压旧token并混配新状态，不会偷偷扩大内存、不补假token。机器人控制不受命令干预。
3. **减轻高频回调。**状态/IMU只缓存不可变消息，推理到达才转换一次；使用单线程短回调。所有已经收到的最新传感器仍可采用，未恢复旧30ms丢行门槛。
4. **提高编码吞吐。**1080p头部4线程，腕部各1线程，仍是原分辨率、原50fps行对应视频、同一官方写入器。未使用未验证的硬件编码器，不改变图像尺寸和训练合同。
5. **保存期间持续排空订阅。**空闲/保存收尾时不把不属于录制的token塞进writer队列，避免下一条接到上一条积压。官方保存忙时额外开始按键会明确提示，未加入逐张JPEG验收。
6. **记录实际耗时。**逐行新增token接收延迟、接收快照到写入的排队时长；每秒状态含add_frame耗时、各视频编码均值/最大值、队列深度和累计等待。便于分清接收、计算、编码与原始源延迟。

过载时明确中断是数据完整性处理，不是50Hz性能已达标的替代品。若真机仍触发该错误，应继续根据计时优化，不能给用户“全部未证实”的含混结果。

## 本地验证证据

- 调整后同类真实RGB纯writer：1000行11.855秒，84.35行/秒；头部encode+mux均值7.47ms，原12.06ms。样本长度不同、同一工作站；只作为定位和性能余量证据，不能写成“真机35→84”。
- 120秒真实ROS/DDS隔离回放：发布6000个token，写入6000行，序号无缺口，实际token跨度约50.00Hz。状态/IMU源各按1kHz发送，三路RGB源约30Hz；数值是合成测试数据，纹理来自现场视频。
- 写入排队P99=4.414ms、最大19.731ms；token接收延迟P99=10.648ms、最大20.697ms；状态相对token最大超前16.955ms，没有旧版的秒级超前。
- 该回放中图像订阅采用latest/BEST_EFFORT，实际接收频率低于发布频率，存在独立图像接收间隙（最坏近0.92秒）。**不能用6000行通过宣称三路图像也无丢帧或全部新鲜。**这与旧token配几秒后的新图像是不同问题；现场需一并查看图像源年龄。没有隐藏这个验证边界。
- 故障回归：快照延迟写入不变；满队列不阻塞接收；过载数据明确interrupted；空闲/保存时500条输入不填队列；旧传感器时间保留、不按30ms删除；重复token不重复写。
- 官方保存/弃用、同条暂停边界、尾帧flush、编码异常、统计和导出回归结果见工作区`VALIDATION.json`与`TEST_RESULTS.json`。版本尚未真机验收。

测试只使用localhost、Domain229、`/offline_bench/*`；未连接机器人、未发真实控制命令。数采程序本身不发布运动指令。

## 现场复测与验收

1. 完成当前采集的保存或弃用，等WAITING_FOR_BUTTON；使用v15安装器更新空闲采集服务。hw、keyboard、SONIC、夹爪不用为安装本修复改参数或重启。
2. 先录一条至少60秒，做正常遥操动作后保存；再录带A+X暂停/恢复的一条。新版本必须打印20261021-collection-15-nonblocking-ingress。
3. 下载时包含日志及source.jsonl。检查写入是否持续约50行/秒、queue是否持续增长、编码及排队耗时、token/state/RGB时间差，而不是只看相邻间隔中位数倒数。
4. 同时用SONIC性能窗口核对模型周期；若身体仍明显迟滞，需要看PICO源帧、接收时序和窗口等待，不能仅凭数采提高认定机器人延迟全部解决。
5. 检查保存/弃用和暂停前后同一episode；导出、真实任务文字与训练加载另外验收。

旧第一条错位数据仅保留诊断，不用于训练。其官方导出和GR00T加载成功没有修复内容错位。
